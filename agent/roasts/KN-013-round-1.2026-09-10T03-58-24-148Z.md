1. Explicit props are the right boundary, but this nine-prop interface is too narrow to become a template. It removes MUI rendering escape hatches, good, but also removes essential native semantics such as `id`, `aria-describedby`, `required`, and `onBlur`. A Button should expose its semantic button surface and intentional design variants, not a giant MUI type nor an arbitrary subset. Do not copy `Frame(mark: string union)` to Buttons or Selects: it becomes a cartesian-state switch and permits invalid combinations. Keep visual state orthogonal, preferably CSS and private data attributes.

2. The `useState` rationale is not right. A plain ref is attached before an effect runs; on a component remount, the ref is attached again and that component’s effect runs again. Nothing breaks with a ref. This implementation schedules an avoidable second render for every mounted Checkbox, so 100 board checkboxes cause 100 local updates and follow-up commits. It is probably not catastrophic, but it is needless hot-path work. Use a callback ref plus an effect, or a ref with a layout effect, and let correctness rather than branch coverage decide the architecture.

3. The selector is already too broad. Its focus rule targets every descendant `.MuiBox-root`, not just the frame. Checked and indeterminate icons each contain a second `Box`, so keyboard focus outlines both the 20px frame and the 12px SVG. See [Checkbox.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.tsx:191). Use a private `data-karnama-checkbox-frame` marker and target that. `:hover` and `:focus-within` on the root avoid both MUI state class strings and reliance on `MuiBox-root`.

4. The real input is correctly exposed as mixed: this component sets the native property, and current MUI also sets `aria-checked="mixed"` for indeterminate controls. The author’s claim that MUI tells assistive technology “unchecked” is false, see [MUI Checkbox](D:/Kar/Gandom/KarNama/node_modules/@mui/material/Checkbox/Checkbox.js:172). The accessibility failures are naming and target size: the shipped story renders an unnamed checkbox, the public API cannot provide an `id` for a conventional visible-label association, and the actual root hit target is only 20 by 20. A wrapper label is merely an undocumented future usage convention, not a property of this component.

Findings:

- **major** — Keyboard focus draws an extra outline around the tick or dash. Both the outer frame and the nested SVG are `MuiBox-root`, so the selector at [Checkbox.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.tsx:191) matches both. Tab to a checked or indeterminate Checkbox: the white 12px glyph receives its own blue outline. This is a visible incorrect state and demonstrates why the selector is not safely scoped.

- **major** — The component has no accessible-name guarantee and lacks `id`, while its canonical stories exercise unnamed controls. `aria-label` and `aria-labelledby` are optional, [Checkbox.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.tsx:30), and the default/keyboard stories render neither, [Checkbox.stories.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.stories.tsx:19). A board card needs, for example, “Select Senior React developer at X”, and a column header needs “Select all Applied jobs.” The component should support `id` and require or enforce an accessible-name strategy at each usage.

- **major** — The 20 by 20 root is also the interactive target because padding is explicitly zero, [Checkbox.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.tsx:179). That misses WCAG 2.5.8’s 24 CSS-pixel target unless each eventual placement demonstrably qualifies for the spacing exception. “A label will wrap it” is neither implemented nor sufficient for icon-only card controls.

- **minor** — Hover, one of the five required Figma states, has no story. The five exports are Unchecked, Checked, Indeterminate, Disabled, and KeyboardOnly, [Checkbox.stories.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.stories.tsx:19). `KeyboardOnly` is valuable behavior coverage, but it is not the Hover state. Consequently the verifier’s “five stories” check does not establish all five design states.

- **minor** — This change directly violates the repository’s “documentation lives in markdown” rule. The component contains long API/design documentation blocks, beginning at [Checkbox.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.tsx:5), despite [AGENTS.md](D:/Kar/Gandom/KarNama/AGENTS.md:117) requiring user-facing component prose in `story-docs`. The same problem appears throughout the stories.

- **minor** — `onChange` has no `fn()` in shared story args and no assertion of its documented `(event, checked)` contract. [Checkbox.stories.tsx](D:/Kar/Gandom/KarNama/apps/web/src/shared/checkbox/Checkbox.stories.tsx:5) violates the repository rule that every callback prop be wired to Storybook Actions.
