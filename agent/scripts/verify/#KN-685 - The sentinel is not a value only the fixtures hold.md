# KN-685 · The Persian sentinel is not a value only the fixtures hold, so the exit condition's claim is false

medium, 1 point, web, OKR-1. A child of KN-062, filed by the whole-task round that followed KN-306's
close.

## The card, quoted

**Why.** "A sentinel that something else in the repository also holds is one edit away from a scan
that reports a leak which is not there, or a reader concluding the value is fixture-only when it is
not. The exit condition is the thing the next person trusts about what the check means."

**Exit.** "The verifier's sentinels are values that appear in no file outside the fixtures' own JSON,
established by a search across the whole repository rather than one directory, with the verifier's
own comments not reintroducing the value they describe; and the card and comments say only what that
search supports."

## The search across the whole repository

Run from a script in the scratchpad, over `git ls-files -z --cached --others --exclude-standard`:
tracked files **plus non-ignored untracked ones**. That is exact, excludes `node_modules` and build
output by construction, and does not depend on me listing directories correctly, which is the failure
this card exists for. Compared as UTF-8 bytes rather than decoded text, the rule `bundle-scan.mjs`
already states.

**`--others` is the plan review's second correction and it matters more than it looks.** The first
version searched `git ls-files` alone, which is tracked files only. The file likeliest to hold a
chosen value by accident is a plan or an evidence draft written during this very task, and such a file
is UNTRACKED at the moment the search runs. This plan was itself untracked when the first search
passed, so that search could not have caught the one mistake it exists to catch.

The English sentinel is in **6** files, the Persian in **8**. Only one of each is a fixture JSON. The
rest: `.claude/todo.db` and `agent/TODO_BOARD.md`, because a card's description is stored and then
rendered; `agent/STATE.md`; the KN-306 plan beside this one; **`agent/scripts/verify/KN-306.mjs`
itself**, in the comment explaining why the sentinel must be per language; and for the Persian,
`apps/web/e2e/written-dates.spec.ts` and `agent/roasts/KN-305-roast.md`.

So the card's finding holds, and one site wider than it states: the card says only the English value
was reintroduced by the verifier's own comment. **Both were.**

## The first draft of this plan was wrong, and the review caught it

I wrote that the exit condition is **unsatisfiable**: `todo render` writes every description into the
board, so naming a sentinel is what puts it outside the fixtures' JSON, and the card's own three
candidates are already there for exactly that reason. From that I concluded no value could qualify and
proposed rewriting the exit around a different property.

**That is a false generalisation and the premise of the whole plan.** The three named values are
disqualified; a value that is never named is not. The exit is satisfiable by a fresh pair written only
into the two JSON files and kept out of every piece of prose. The correction is adopted whole, and the
exit is **not** amended.

Two further corrections, both taken:

- I described the build's sourcemap as the record of "everything Vite read". It is not. Vite copies
  `public/`, inlines small assets and emits generated bytes, none of which appear as a `sources`
  entry. That is absolute coverage language on a partial mechanism, the failure `AGENTS.md` section 7
  records against me repeatedly, written this time inside the card whose subject is a false coverage
  claim.
- `scanBundle` already reads **every regular file** under `dist`, HTML included, so the `servedPages`
  helper I proposed added no coverage at all.

**The sourcemap machinery is dropped entirely.** No new helper, no new check, no change to
`bundle-scan.mjs`.

## The values, and why they are not written here

Four candidate pairs, each one company named in English and in Persian, were searched across all 1280
tracked files from the scratchpad script, outside the repository. All four appear in **zero** files.
One pair is chosen.

**The chosen values are deliberately not written in this plan, in the card, in its evidence, in
`STATE.md` or in the commit message.** Writing them down is precisely what disqualified the card's own
three candidates, so recording them anywhere would undo the work in the act of reporting it. They will
exist in two files: `en-US.json` and `fa-IR.json`. Anyone can recover them by opening those files, and
the claim is re-checkable by re-running the search.

## What I checked before touching product data

The card asks for replacements, and fixture data is sample data that stories draw, so the risk is a
story that depends on the value rather than on the field. Each checked by search, not by assumption:

- **No literal assertion anywhere.** Every consumer is derived: `set.jobs[0]?.company` typed into a
  form, `job.company` passed to a card. The whole-repository search above lists every file holding
  either value, and no story or test is among them.
- **The length floor.** `story-fixtures.test.ts` line 206 requires the longest company in each set to
  be at least 40 characters. That is `jobs[1]`, which is not touched.
- **The company sort.** `records.ts` line 165 sorts by `company.localeCompare`, and
  `records.test.ts` line 133 asserts a company sort over its own `a` and `b` jobs, not over the
  fixtures. No story asserts a company-ordered board.
- **The `«آسمان»` search fragment.** Three `JobsScreen` plays type it and their comments depend on it
  being in the second and fourth companies and nothing else the board is seeded with. The chosen pair
  does not contain it, and the script refuses a candidate that does.
- **`written-dates.spec.ts` seeds its own literal** and never reads the fixtures, so it cannot break.

## File by file

- `apps/web/src/shared/story-fixtures/en-US.json` and `fa-IR.json` — the first job's `company`, and
  the first contact's `company` with it. Both, because `contact-1` carries `jobId: job-1` and names
  that employer: changing one and not the other would leave the sample data self-contradictory.
- `agent/scripts/verify/KN-306.mjs` — **comments only, no behaviour.** The `sentinels()` docblock
  keeps the per-language reasoning and stops quoting either value; the header's quoted exit condition
  and the closing paragraph say what is now true.
- `agent/scripts/verify/#KN-306 - ....md` — the paragraph at lines 45 to 48 names the old sentinels as
  the values that are fixture-only, which this change makes false. Corrected in place, describing the
  requirement rather than the values. The record stays, per the rule that a stale plan is corrected
  and never removed.
- **KN-306's board evidence**, through `todo edit KN-306 --evidence` and then `todo render`, never by
  hand-editing the rendered board, which is generated. Its evidence says the sentinels are read from
  the fixtures' own JSON "since en-US holds X where fa-IR holds Y", naming both: a present-tense claim
  about what the check uses, which this change makes false. The replacement states the derivation and
  the per-language requirement without naming a value. **KN-306's exit condition is left exactly as
  it is**: "a sentinel only the fixtures hold" is the thing this card makes TRUE, so it needs no
  rewording, and rewording a closed card's exit to match new work is the move I was rightly stopped
  from making with this card's own.
- `agent/STATE.md` — its "Sentinels must be per language" lines name both values as the sentinels, in
  the present tense. Rewritten in the step 7 rewrite this iteration ends with, without naming the new
  pair.
- This plan.
- **Not changed:** `written-dates.spec.ts` and `agent/roasts/KN-305-roast.md`, which use or discuss the
  old Persian text but never claim it is the current sentinel and take no part in the check, so the
  value there is simply record data once this lands; any story; any other fixture row;
  `bundle-scan.mjs`.

**Both of round two's corrections are adopted verbatim and neither adds a design decision**, which is
why this goes to the build rather than to a third review round: the search set is widened, and two
stale present-tense claims join the change.

## What I expect to be hard, and what I am unsure about

- **The discipline is the deliverable, and it is fragile.** The property holds only while nobody
  writes the value into prose. The next iteration writing a helpful sentence in `STATE.md` breaks it
  silently. I do not have a way to make that fail loudly without the run-time check the review just
  told me not to add, and I think accepting that is right for a one point card, but it is the thing I
  am least comfortable with.
- **The old values stay behind** in the e2e spec, the archived roast, the board, `STATE.md` and the
  KN-306 plan. They stop being sentinels, so they are harmless, but a reader meeting
  `«فناوران نوین پارس»` in `written-dates.spec.ts` may still take it for one.

## How I will know it worked

- **Re-run the same whole-repository search after the edit**: each sentinel in exactly one tracked
  file, its own locale JSON. The same script, so the before and after are measured the same way.
- **The KN-306 verifier**, unchanged in behaviour, run whole: three builds, its clean scan, its
  planted-import failure and its byte-for-byte restore, read from its own printed lines.
- **The unit project**, which holds `story-fixtures.test.ts` and the records tests, read from the
  summary line and refused on "skipped" or a zero total.
- The fixture-reading stories of `JobsScreen` and `NetworkScreen`, for the same reason.
- `tsc --noEmit` and `eslint --max-warnings 0`, read from their own output lines.

## What I am asking the review

1. Keeping the chosen values out of the plan, the card and the evidence is what makes the exit
   satisfiable, but it also means the next reader is told a property holds for values they are never
   shown. Is that discipline sound, or is it a kind of unverifiability traded for a satisfied clause?
2. Is there a class of fixture consumer I have not checked? I checked literal assertions, the length
   floor, the company sort and the search fragment.
3. The review said a run-time uniqueness check is not needed for this card and should not replace the
   literal proof. Agreed and dropped. But is establishing the property **once, by a search** the right
   end state, given nothing then stops it decaying?
4. The old values remain in the e2e spec, the board and two plans. Leave them, or is a stale value
   that still looks like a sentinel the same defect this card is about?
